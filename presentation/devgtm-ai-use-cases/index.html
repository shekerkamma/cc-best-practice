Design Decision

Why domain as the join key?

The three alternatives considered
✗Company name — fails on spelling variants, subsidiaries, legal entity differences
✗D&B / DUNS identifier — precise but requires paid enrichment on every record
✓Company domain — covers the vast majority of B2B accounts, available in every integration, free
When it works well
Direct company email domains where stripe.com = stripe.com across all six sources. Covers 85–90% of typical B2B account lists without any manual intervention.
Known failure cases
⚠Subsidiaries — child company email differs from parent domain used in CRM
⚠Personal emails — contacts using @gmail.com or @yahoo.com cannot be matched
⚠Rebrands — company changed domain name; old records don't reconcile automatically
The mitigation
domain_mappings includes a manual override layer. Operators explicitly link variant domains (e.g. old-name.com → new-name.com) or subsidiary domains to the canonical account. A deliberate pragmatic trade-off: broad coverage now, precision via override.

Stack Choice

Deterministic plumbing + probabilistic reasoning

Built in 26 Claude prompts inside Lovable. Clean separation between what should be deterministic and what benefits from AI flexibility.

🏗️
Lovable
Deterministic Plumbing
Handles UI scaffolding, data flows, authentication (email/password + Google OAuth), integration sync logic, and Supabase edge functions. Everything that should behave identically every time.
▸ Dark navy design system (hsl 232 30% 10%)
▸ 26 discrete implementation steps, one prompt each
▸ Route protection + role-based access
▸ Secrets via Lovable Cloud — never hardcoded
🧠
Claude
Probabilistic Reasoning
Handles research synthesis, pitch generation, intent explanation, and conversational Q&A. Everything that benefits from reasoning flexibility rather than rigid rules. Model: claude-3-5-sonnet.
▸ Streaming API (SSE) for real-time chat responses
▸ Structured output for enrichment fields
▸ Account context as system prompt for grounded answers
▸ ANTHROPIC_API_KEY via Lovable Cloud secrets

Key Takeaways

Three principles that make AI GTM work

01
Normalize First
No amount of AI reasoning compensates for fragmented, inconsistent source data. Domain-match normalization is the prerequisite for every other use case in this stack. Build the data foundation before the AI layer.
02
AI as the Read Layer
The highest-leverage AI applications in DevGTM Mesh are read actions — research synthesis, pitch generation, conversational analytics. The AI reads the normalized data and surfaces insight. It does not replace the data layer; it interprets it.
03
Agentic UI as Endpoint
The goal is not a smarter dashboard — it is a system that knows what to surface, when to surface it, and can act on it when asked. The AI-first dashboard and global chat panel are the interface expression of the Normalize → Score → Reason → Act stack.
